## สรุปสำหรับผู้บริหาร

ระบบผ่านการตรวจ **14 จาก 17 หัวข้อ** ที่กำหนดไว้

| ระดับ | จำนวน | ความหมาย |
|---|---|---|
| ✅ ผ่าน | 14 | ทำงานถูกต้องและมีหลักฐานการทดสอบ |
| ⚠️ ต้องทำก่อนเปิดใช้จริง | 3 | ไม่ใช่ช่องโหว่ของโค้ด แต่เป็นการตั้งค่าที่ยังไม่ครบ |
| ❌ ช่องโหว่ที่ยังแก้ไม่ได้ | 0 | — |

**ข้อสรุป:** โค้ดไม่มีช่องโหว่ที่ทราบ แต่**ยังเปิดใช้งานจริงไม่ได้**
จนกว่าจะจัดการ 3 ข้อในหัวข้อ "สิ่งที่ต้องทำก่อนเปิดใช้จริง" ให้ครบ

## 2. การป้องกันการโจมตี

| # | หัวข้อ | ผล | หลักฐาน |
|---|---|---|---|
| 2.1 | SQL Injection | ✅ | ใช้ Drizzle ORM ที่ส่งค่าแบบ parameterized ทุกจุด ไม่มีการต่อสตริง SQL เอง |
| 2.2 | XSS | ✅ | React หลบอักขระพิเศษให้อัตโนมัติ · ไม่มีการใช้ `dangerouslySetInnerHTML` ที่รับค่าจากผู้ใช้ |
| 2.3 | CSRF | ✅ | ใช้ Server Actions ของ Next.js ซึ่งตรวจ Origin ให้เอง · คุกกี้ตั้ง `sameSite: lax` |
| 2.4 | Rate limiting | ✅ | `src/lib/rate-limit.ts` · **ทดสอบจริงแล้ว บล็อกที่ครั้งที่ 41 พอดี** |
| 2.5 | ไฟล์อัปโหลดที่ฝังสคริปต์ | ✅ | ถอด `<script>` และ event handler ออกจาก SVG · ทดสอบใน `e2e-admin-media` |
| 2.6 | ป้องกัน bot ที่ฟอร์ม | ⚠️ | มี honeypot แล้ว แต่ยังไม่ได้ตั้ง reCAPTCHA (ดูข้อ 5.3) |

### รายละเอียด Rate limiting

| จุด | เพดาน | เหตุผลที่ตั้งเท่านี้ |
|---|---|---|
| ลงทะเบียน | 40 ครั้ง / 10 นาที | คนหน้างานหลายสิบคนใช้ Wi-Fi เดียวกัน ระบบเห็นเป็น IP เดียว |
| ล็อกอิน | 40 ครั้ง / 10 นาที | เจ้าหน้าที่ทั้งทีมล็อกอินจากเครือข่ายเดียวกันตอนเปิดงาน |
| รายชื่อสำรอง | 20 ครั้ง / 10 นาที | ใช้น้อยกว่าและไม่ใช่ทางที่คนหน้างานต้องใช้พร้อมกัน |

> **ข้อควรรู้:** ตัวเลขตั้งไว้สูงโดยตั้งใจ เพราะ "หนึ่ง IP ไม่เท่ากับหนึ่งคน"
> ถ้าตั้งต่ำ คนที่มาลงทะเบียนหน้างานคนที่ 9 เป็นต้นไปจะลงทะเบียนไม่ได้เลยทั้งงาน
> ด่านนี้จึงกัน "สคริปต์ที่ยิงเป็นพันครั้ง" ส่วนการเดารหัสผ่านรายบัญชี
> มีระบบล็อกบัญชี (ข้อ 1.2) คุมอยู่แล้วซึ่งแม่นยำกว่า

## 3. Security Headers

ตรวจอัตโนมัติทุกครั้งด้วย `node tests/e2e-security.mjs` — ผ่านครบ 9 ข้อ

| Header | ค่า | ป้องกันอะไร |
|---|---|---|
| `Strict-Transport-Security` | max-age 1 ปี | บังคับ HTTPS กันการดักกลางทาง |
| `Content-Security-Policy` | ดูด้านล่าง | ด่านสุดท้ายกัน XSS |
| `X-Frame-Options` | DENY | กันเว็บอื่นเอาหน้าเราไปฝังหลอกผู้ใช้ |
| `X-Content-Type-Options` | nosniff | กันเบราว์เซอร์เดาชนิดไฟล์ผิด |
| `Referrer-Policy` | strict-origin-when-cross-origin | ไม่ส่ง URL เต็มไปเว็บอื่น |
| `Permissions-Policy` | ปิดไมค์และตำแหน่ง เปิดกล้องเฉพาะโดเมนตัวเอง | กล้องจำเป็นสำหรับสแกน QR |

**ข้อจำกัดที่ยอมรับไว้ใน CSP:**

`script-src` ต้องมี `'unsafe-inline'` และ `'unsafe-eval'` เพราะ Next.js
ฝังสคริปต์ที่ทำให้หน้าเว็บโต้ตอบได้ไว้ในหน้าโดยตรง ถอดออกแล้วเว็บจะใช้งานไม่ได้เลย
ความเสี่ยงที่เหลือถูกชดเชยด้วยข้อ 2.2 (React หลบอักขระให้อยู่แล้ว)

`upgrade-insecure-requests` เปิดเฉพาะบนเครื่องจริง เพราะบนเครื่องพัฒนา (http)
คำสั่งนี้จะทำให้ service worker แคชหน้าไม่ได้ ส่งผลให้ทดสอบโหมดออฟไลน์ไม่ได้เลย

## 4. ข้อมูลส่วนบุคคล (PDPA)

| # | หัวข้อ | ผล | หลักฐาน |
|---|---|---|---|
| 4.1 | ไม่เก็บ IP ดิบ | ✅ | แฮชก่อนบันทึกทุกจุด รวมถึงตารางตัวนับ rate limit |
| 4.2 | หลักฐานความยินยอม | ✅ | ตาราง `consents` เก็บว่ายินยอมข้อไหน เมื่อไร นโยบายเวอร์ชันใด |
| 4.3 | แยกความยินยอมถ่ายภาพออกจากการลงทะเบียน | ✅ | ไม่ยินยอมก็ยังลงทะเบียนได้ |
| 4.4 | ลบข้อมูลตามคำขอ | ✅ | ปุ่มในหน้าหลังบ้าน · ลบชื่อ/อีเมล/เบอร์ แต่คงยอดสถิติไว้ |
| 4.5 | ลบอัตโนมัติเมื่อครบกำหนด | ✅ | ตั้งจำนวนวันได้ที่หน้าตั้งค่า · ทำงานในงานรายวัน · **ทดสอบแล้วว่ารันซ้ำไม่ลบซ้ำ** |
| 4.6 | บันทึกทุกครั้งที่เข้าถึงหรือส่งออกข้อมูล | ✅ | ตาราง `audit_logs` · ทดสอบใน `e2e-admin-flow` ข้อ ⑨ |
| 4.7 | หน้านโยบายความเป็นส่วนตัว | ⚠️ | หน้ามีแล้ว แต่**ยังเป็นแบบร่าง** (ดูข้อ 5.1) |

## 5. สิ่งที่ต้องทำก่อนเปิดใช้จริง

### 5.1 ⚠️ เติมข้อมูลในนโยบายความเป็นส่วนตัวและเงื่อนไขการใช้งาน

หน้า `/privacy` และ `/terms` เขียนโครงไว้ครบตามที่ระบบเก็บข้อมูลจริง
แต่ยังมีช่องว่างในวงเล็บเหลี่ยม `[ ]` ที่ต้องเติมเอง:

- ชื่อและที่อยู่องค์กรผู้ควบคุมข้อมูล
- อีเมลและเบอร์ติดต่อผู้รับผิดชอบข้อมูลส่วนบุคคล
- จำนวนวันที่จะเก็บข้อมูล
- นโยบายการยกเลิกและคืนเงิน (ถ้ามีค่าลงทะเบียน)

**ต้องให้ฝ่ายกฎหมายตรวจก่อนเปิดรับลงทะเบียนจริง** — เป็นเอกสารผูกพันทางกฎหมายขององค์กร
ซึ่งผู้พัฒนาระบบเขียนแทนไม่ได้

### 5.2 ⚠️ เปลี่ยนความลับที่เคยปรากฏในภาพหน้าจอ

ระหว่างการตั้งค่าร่วมกัน มีค่าลับ 3 ตัวปรากฏในภาพหน้าจอที่ส่งผ่านช่องทางแชต

| ค่า | ผลถ้าหลุด |
|---|---|
| รหัสผ่านฐานข้อมูล Supabase | เข้าถึงข้อมูลผู้ลงทะเบียนทั้งหมดได้ |
| `SESSION_SECRET` | ปลอมเป็นผู้ดูแลระบบได้โดยไม่ต้องรู้รหัสผ่าน |
| `HASH_SALT` | ย้อนหาเจ้าของ IP ที่แฮชไว้ได้ง่ายขึ้น |

**วิธีแก้:** สร้างค่าใหม่ทั้ง 3 ตัว แล้วอัปเดตทั้งใน `.env.local` และ Environment Variables บน Vercel

```
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # HASH_SALT
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"   # SESSION_SECRET
```

> ⚠️ เปลี่ยน `HASH_SALT` แล้ว ค่าแฮชเดิมจะเทียบกับของใหม่ไม่ได้
> ควรเปลี่ยน**ก่อน**เริ่มรับลงทะเบียนจริง ไม่ใช่ระหว่างทาง

### 5.3 ⚠️ ตั้ง reCAPTCHA และปิดบัญชีตัวอย่าง

- ยังไม่ได้ตั้ง `RECAPTCHA_SECRET_KEY` — ตอนนี้กัน bot ด้วย honeypot อย่างเดียว
- บัญชี `admin@example.com` และ `staff@example.com` เป็นบัญชีตัวอย่าง
  **ต้องสร้างบัญชีด้วยอีเมลจริงของทีม แล้วปิดบัญชีตัวอย่างทิ้ง**

## 6. การเข้าถึงสำหรับผู้พิการ (WCAG 2.1 AA)

ตรวจอัตโนมัติด้วย `npm run check:contrast` — **ผ่านครบ 10 คู่สี**

การแก้ไขที่ทำในรอบนี้:

| สี | เดิม | ใหม่ | ค่าที่ได้ |
|---|---|---|---|
| ตัวหนังสือจาง | `#857a71` | `#7c7168` | 4.18 → 4.75 |
| สีธีมเข้ม | `#c94a18` | `#be4515` | 4.25 → 4.70 |
| สีข้อความเตือน | `#d32f2f` | `#c62828` | 4.39 → 4.96 |
| เส้นขอบช่องกรอก | `#d6ccc2` | `#95897b` | 1.58 → 3.42 |

**สีแบรนด์ `#EC5F27` คงไว้เหมือนเดิมทุกประการ** — ตัวหนังสือขาวบนสีนี้ได้ 3.37:1
ซึ่งไม่ผ่านเกณฑ์ตัวหนังสือขนาดปกติ (4.5:1) แต่ผ่านเกณฑ์ตัวหนังสือขนาดใหญ่ (3:1)
จึงกำหนดให้ตัวหนังสือบนปุ่มสีธีมเป็น **19px ตัวหนา** ซึ่ง WCAG นับเป็นขนาดใหญ่

สิ่งที่ทำไว้ก่อนหน้าและยังใช้ได้:
- เส้นขอบโฟกัสมองเห็นชัดทุกปุ่มและช่องกรอก
- รองรับ `prefers-reduced-motion` สำหรับผู้ที่เวียนหัวจากภาพเคลื่อนไหว
- ปุ่มและช่องกรอกสูงอย่างน้อย 44px ตามเกณฑ์การกดบนมือถือ

**ยังไม่ได้ตรวจ:** การใช้งานด้วยโปรแกรมอ่านหน้าจอจริง (NVDA / VoiceOver)
ซึ่งต้องทดสอบด้วยคนจริง ไม่สามารถตรวจอัตโนมัติได้ — แนะนำให้ทำในเฟส 7

## 7. สิ่งที่ยังไม่ได้ตรวจ และเหตุผล

| หัวข้อ | ทำไมยังไม่ตรวจ |
|---|---|
| การทดสอบเจาะระบบโดยบุคคลที่สาม | ต้องจ้างผู้เชี่ยวชาญภายนอก อยู่นอกขอบเขตของการพัฒนา |
| การกู้คืนข้อมูลจาก backup | ต้องทดสอบบนฐานข้อมูลจริงหลังตั้งค่า backup ของ Supabase แล้ว |
| ความปลอดภัยของ Cloudflare R2 | ยังไม่ได้ตั้งค่า (ดูขั้นตอนที่ 6 ใน `docs/DEPLOY.md`) |
| โปรแกรมอ่านหน้าจอ | ต้องใช้คนจริงทดสอบ |
| การรับภาระเมื่อมีคนเข้าพร้อมกันจำนวนมาก | ทดสอบการตัดโควตาพร้อมกัน 60 คำขอแล้ว แต่ยังไม่ได้ทดสอบระดับพันคน |

## วิธีตรวจซ้ำเอง

```
npm run check:contrast          # ตรวจค่าความต่างของสี
node tests/e2e-security.mjs     # ตรวจ headers · rate limit · หน้านโยบาย
npm run check:deploy            # ตรวจว่าตั้งค่าครบก่อน deploy
npm audit                       # ตรวจช่องโหว่ของไลบรารีที่ใช้
```

ควรรันทั้ง 4 คำสั่งนี้ทุกครั้งก่อน deploy ขึ้นเครื่องจริง
